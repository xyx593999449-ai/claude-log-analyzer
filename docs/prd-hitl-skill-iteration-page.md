# PRD：HITL 数字员工 Skill 迭代运营页

## 1. 背景 / 概述

当前 `Claude Log Analyzer` 已具备批次概览、任务看板和日志下钻能力，能够帮助业务专员查看大 POI 核实链路中的执行状态、异常分布和底层日志细节。

但当前系统仍缺少一个独立页面，用来承接“基于人工作业反向迭代数字员工 Skill”的闭环运营过程。现有页面更偏任务执行观察与问题排查，无法系统展示以下关键流程：

- 基于一段时间内人工核实/复核结果形成独立的迭代批次
- 结合历史数字员工执行日志，由大模型分别分析核实 Skill 与质检 Skill 的执行问题
- 输出核实 / 质检两套 Skill 的迭代建议并形成候选版本
- 使用联合回归样本集验证两套 Skill 新版本
- 输出核实回归是否通过、质检回归是否通过，以及整体上线 / 暂缓 / 回滚结论

本次需求新增一个独立页面，用于展示并运营这一套 `Human-in-the-Loop (HITL)` 闭环数据飞轮 / 数字员工运营飞轮。页面目标不是取代现有任务看板，而是作为“数字员工持续迭代运营台”，帮助业务、产品和算法协同判断本轮迭代是否值得上线。

---

## 2. 目标

- 将“人工反馈结果池 -> 大模型分析 -> Skill 迭代 -> 联合回归 -> 发布决策”可视化为一个完整独立页面。
- 以 `大 POI 核实场景` 为单一业务域，统一展示核实 Skill 与质检 Skill 的双链路闭环。
- 明确区分“任务执行批次”与“迭代批次”，避免概念混淆。
- 支持对单个 `迭代批次` 查看其样本范围、问题归因、迭代建议、版本产出和联合回归结论。
- 在一次联合回归验证中分别给出 `核实 Skill` 与 `质检 Skill` 的通过结果，并收敛为一个最终发布决策。

---

## 3. 用户与使用场景

### 3.1 目标用户

- 数字员工运营负责人
- 产品经理 / 业务负责人
- Skill 研发与维护人员
- 参与人工复核与回归验收的协同角色

### 3.2 核心使用场景

- 运营负责人按一段时间窗口汇总人工核实结果，形成一个新的 `迭代批次`
- 团队查看该批次下核实 / 质检两套 Skill 的问题画像和 LLM 迭代建议
- Skill 维护人员查看候选版本的变更摘要与预期收益
- 团队完成一次联合回归验证，并分别判断核实 / 质检是否通过
- 管理者基于分项结果和整体风险做出上线、暂缓或回滚结论

## 4. 方案比较

### 方案 A：总览 + 双栏并行 + 联合回归发布区

- 概述：页首展示 HITL 闭环总览，中段按“核实 / 质检”并行展示问题分析与迭代建议，底部收敛为一次联合回归验证与最终发布结论。
- 优点：
  - 最符合当前业务的双链路结构
  - 能清晰表达“共享同一人工反馈基准，但分别迭代两套 Skill”
  - 适合运营与发布决策双重场景
- 代价 / 风险：
  - 信息量较大，页面需要控制密度和模块层级
- 适用场景：
  - 当前单一业务域、双 Skill 并行迭代的场景

### 方案 B：总览 + Tab 切换（核实/质检）+ 联合回归发布区

- 概述：页首保留 HITL 总览，中段通过 Tab 切换查看核实或质检侧分析，底部仍为联合回归与发布结论。
- 优点：
  - 页面更紧凑
  - 第一版实现成本较低
- 代价 / 风险：
  - 核实与质检之间的对照关系变弱
  - 不利于同时观察两套 Skill 的问题结构
- 适用场景：
  - 信息量极大、必须压缩主屏复杂度时

### 方案 C：总览 + 时间轴闭环页

- 概述：围绕一次迭代批次，用时间轴串起人工反馈、LLM 分析、Skill 候选版本、联合回归和发布结论。
- 优点：
  - 叙事感强，适合汇报
  - 闭环路径清晰
- 代价 / 风险：
  - 承载运营分析细节的能力弱于方案 A
  - 不利于做指标对比和问题聚类
- 适用场景：
  - 偏对外汇报或复盘展示时

### 推荐方案

采用 `方案 A：总览 + 双栏并行 + 联合回归发布区`。

原因：

- 它最能体现本需求的核心结构：共享同一人工反馈结果池，分别输出核实 / 质检两套 Skill 的分析、建议与版本迭代。
- 它兼顾“运营分析”和“发布决策”两个场景，不会把页面做成纯展示页。
- 相比 Tab 方案，它更容易表达两条链路的对应关系；相比时间轴方案，它更利于日常运营使用。

## 5. 页面定位

该页面是一个新增的独立页面，定位为：

`大 POI 核实场景下，面向双 Skill（核实 / 质检）的 HITL 迭代运营与发布决策页。`

页面应满足以下定位边界：

- 它不是任务执行明细页
- 它不是单纯的流程概念展示页
- 它不是代码版本管理页
- 它是围绕“迭代批次”组织的信息聚合页

---

## 6. 信息架构

### 6.1 页首总览区

展示当前页面是什么、当前迭代批次是谁、其覆盖范围和当前状态。

建议包含：

- 页面标题与说明
- 当前迭代批次 ID / 名称
- 时间范围
- 人工反馈样本量
- 历史执行日志样本量
- 当前批次状态：分析中 / 建议已产出 / 候选版本已生成 / 联合回归中 / 已完成决策
- 一张 HITL 流程总览卡：
  - 人工反馈结果池
  - LLM 分析
  - 核实 Skill 迭代建议
  - 质检 Skill 迭代建议
  - 新版本 Skill 产出
  - 联合回归验证
  - 最终发布决策

### 6.2 迭代批次摘要区

说明本轮迭代为何发起，以及本轮分析样本的构成。

建议包含：

- 迭代批次目标
- 样本来源说明
- 时间窗定义
- 人工问题类型概览
- 历史日志覆盖范围
- 本轮是否达到发起迭代门槛

### 6.3 问题分析区

页面主体采用双栏或上下双分区，分别展示：

- 核实 Skill 问题分析
- 质检 Skill 问题分析

每块建议包含：

- 人工发现的问题分布
- 问题数量 / 占比 / 严重度
- 结合历史日志的根因归纳
- 大模型总结出的执行问题
- 典型案例或证据摘要

### 6.4 迭代建议区

仍按核实 / 质检两块展示，每条建议结构化表达。

每条建议建议包含：

- 建议标题
- 对应问题
- 根因判断
- 建议改动点
- 预期收益
- 风险或副作用
- 是否纳入本次候选版本

### 6.5 Skill 版本产出区

展示本轮候选版本的变更摘要，而不是直接展示底层代码差异。

建议包含：

- 核实 Skill：基线版本 -> 候选版本
- 质检 Skill：基线版本 -> 候选版本
- 每套 Skill 的能力变更摘要
- 重点改动点
- 风险提示

### 6.6 联合回归验证区

这是一次联合回归动作，不是两次完全独立的验证流程。

页面需先给出联合回归总览，再分别展示核实 / 质检分项结果。

建议包含：

- 回归样本集规模
- 覆盖问题类型
- 回归执行状态
- 核实回归结果
- 质检回归结果

### 6.7 发布结论区

该区域用于输出最终决策。

建议包含：

- 整体发布结论：可上线 / 有条件上线 / 暂缓上线 / 回滚 / 维持旧版
- 核实 Skill 回归是否通过
- 质检 Skill 回归是否通过
- 决策依据摘要
- 后续动作建议

## 7. 数据对象定义

### 7.1 人工反馈结果池

定义：一段时间内人工核实 / 复核后形成的真实结果集合，是本页面的上游基准输入。

说明：

- 与数字员工的任务执行批次无直接一一对应关系
- 可跨多个任务批次汇总形成一个新的迭代批次

### 7.2 迭代批次

定义：基于一段时间窗口内的人工反馈结果池和历史执行日志，形成的一次完整分析、建议、Skill 迭代和回归验证单元。

说明：

- 是本页面的主组织对象
- 不等同于任务执行批次

### 7.3 候选 Skill 版本

定义：基于当前迭代批次的分析和建议，分别产出的核实 Skill / 质检 Skill 新版本。

### 7.4 联合回归验证

定义：针对本轮两套候选 Skill 新版本开展的一次统一回归评测动作。

说明：

- 同一次验证中分别输出核实是否通过、质检是否通过
- 最终用于支撑统一发布结论

### 7.5 发布结论

定义：基于联合回归验证结果得出的整体上线判断。

## 8. 用户故事

### US-001：查看迭代批次总览
**描述：** 作为数字员工运营负责人，我想查看某个迭代批次的总览信息，以便快速理解本轮闭环的范围、状态和目标。

**验收标准：**
- [ ] 页面可展示当前迭代批次的名称或 ID、时间范围、样本量和当前状态
- [ ] 页面可用一段清晰说明解释该页是 HITL 数字员工 Skill 迭代运营页
- [ ] 页首存在流程总览模块，能展示从人工反馈到发布结论的完整闭环
- [ ] 仅 UI 变更：使用 dev-browser skill 做浏览器验证

### US-002：分别查看核实与质检的问题分析
**描述：** 作为 Skill 维护人员，我想分别查看核实 Skill 和质检 Skill 的问题分析结果，以便定位两套 Skill 各自的主要问题。

**验收标准：**
- [ ] 页面需分别展示核实侧和质检侧的问题分析区域
- [ ] 每个区域至少包含问题分布、严重度或频次、日志归因和证据摘要
- [ ] 页面需清晰标识核实和质检两条链路，避免信息混淆
- [ ] 仅 UI 变更：使用 dev-browser skill 做浏览器验证

### US-003：查看结构化迭代建议
**描述：** 作为产品经理，我想查看大模型对核实 / 质检两套 Skill 输出的结构化迭代建议，以便判断本轮迭代范围是否合理。

**验收标准：**
- [ ] 页面需分别展示核实 Skill 和质检 Skill 的迭代建议
- [ ] 每条建议至少包含问题、建议改动点、预期收益和风险
- [ ] 页面可标识某条建议是否进入本次候选版本
- [ ] 仅 UI 变更：使用 dev-browser skill 做浏览器验证

### US-004：查看候选 Skill 版本摘要
**描述：** 作为 Skill 研发人员，我想查看核实与质检候选版本相对基线版本的变更摘要，以便理解本轮发布内容。

**验收标准：**
- [ ] 页面分别展示核实 Skill 与质检 Skill 的基线版本和候选版本
- [ ] 每套 Skill 都有对应的能力变更摘要
- [ ] 页面重点突出“变更摘要”而非底层代码 diff
- [ ] 仅 UI 变更：使用 dev-browser skill 做浏览器验证

### US-005：查看联合回归与最终发布结论
**描述：** 作为发布决策人，我想查看一次联合回归验证中的核实 / 质检分项结果，以及整体发布结论，以便决定是否上线。

**验收标准：**
- [ ] 页面存在联合回归验证总览区，说明回归样本规模、覆盖范围和执行状态
- [ ] 页面分别展示核实回归结果与质检回归结果
- [ ] 页面展示整体发布结论，并附带决策依据摘要
- [ ] 当核实与质检结果不一致时，页面仍能清晰展示分项通过情况与整体结论
- [ ] 仅 UI 变更：使用 dev-browser skill 做浏览器验证

## 9. 功能需求

- `FR-1`：系统必须新增一个独立页面，用于承接 HITL 数字员工 Skill 迭代运营闭环。
- `FR-2`：系统必须以 `迭代批次` 作为页面主组织对象，而非任务执行批次。
- `FR-3`：系统必须在页首总览区明确展示当前迭代批次的基础信息、状态和闭环总览。
- `FR-4`：系统必须区分并展示 `核实 Skill` 与 `质检 Skill` 两条分析链路。
- `FR-5`：系统必须展示基于人工反馈结果池与历史日志分析得出的执行问题。
- `FR-6`：系统必须分别展示核实 / 质检两套 Skill 的结构化迭代建议。
- `FR-7`：系统必须分别展示核实 / 质检候选 Skill 版本的变更摘要。
- `FR-8`：系统必须展示一次 `联合回归验证` 的总览信息。
- `FR-9`：系统必须在联合回归验证中分别输出 `核实回归是否通过` 与 `质检回归是否通过`。
- `FR-10`：系统必须基于联合回归结果给出一个整体发布结论。
- `FR-11`：当核实 / 质检分项结果不一致时，系统必须同时展示分项结果与整体结论依据。
- `FR-12`：页面文案必须明确区分 `人工反馈结果池`、`迭代批次`、`任务执行批次` 等概念，避免混淆。

---

## 10. 非目标

- 本次不建设通用多业务域平台化能力
- 本次不支持多个数字员工业务域的统一组合管理
- 本次不建设自动生成 Skill 包的完整编排引擎
- 本次不替代现有任务执行看板、批次概览和日志详情页
- 本次不引入底层代码级 diff 审阅能力
- 本次不扩展到除“大 POI 核实”之外的其他业务场景

---

## 11. 设计考虑

### 11.1 视觉与交互

- 页面需延续现有 dashboard 体系的视觉语言，避免成为完全割裂的新系统
- 建议在页首使用高辨识度的流程总览模块，突出“闭环”概念
- 问题分析与迭代建议区建议采用 `核实 / 质检` 并行布局，便于对照
- 当内容过长时，可在局部区域使用折叠或轻量级二级切换控制信息密度

### 11.2 文案与命名

建议优先统一以下对象命名：

- 人工反馈结果池
- 迭代批次
- 候选 Skill 版本
- 联合回归验证
- 发布结论

---

## 12. 技术考虑

- 页面应遵循现有 React + Tailwind 的前端结构和组件风格
- 优先增量扩展当前 dashboard 路由与页面结构，避免无必要的大规模重构
- 需要为“迭代批次”定义独立于任务执行批次的数据模型
- 需要考虑未来支持真实数据接入与 mock 数据占位的兼容方案
- 联合回归验证区的数据模型需同时支持：
  - 一次统一回归动作
  - 核实 / 质检两个分项结果
  - 一个最终发布结论

---

## 13. 成功指标

- 团队可以在单页内完整理解某个迭代批次从人工反馈到发布结论的闭环过程
- 用户无需切换多页即可同时查看核实 / 质检两套 Skill 的问题分析与迭代建议
- 当联合回归完成后，页面可明确说明：
  - 核实是否通过
  - 质检是否通过
  - 整体是否允许上线
- 页面在概念表达上不再混淆“任务执行批次”和“迭代批次”

---

## 14. 风险与约束

- 页面同时承载方法说明、问题分析、版本摘要和发布结论，信息密度较高
- `人工反馈结果池` 与 `任务执行批次` 概念相似，若命名不严谨会造成理解偏差
- 核实 / 质检共用同一人工反馈基准，但实际迭代质量和回归结果可能不一致，需要页面能稳健表达差异
- 若后续扩展到多个业务域，当前单业务域页面结构可能需要进一步抽象

---

## 15. 未决问题

- 迭代批次的唯一标识、命名规则和状态枚举是否已有既定规范
- 联合回归验证的分项指标体系是否已有稳定口径
- 发布结论是否允许出现“部分通过但整体暂缓”的中间状态，以及其展示规则
- 页面第一版是否接真实数据，还是先以静态或 mock 数据完成信息架构验证
