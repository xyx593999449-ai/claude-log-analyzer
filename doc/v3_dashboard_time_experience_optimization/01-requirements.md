# 迭代需求文档：执行流量趋势与时间交互修复优化

## 1. 背景与目标

在最近一版主看板优化能力上线到正式环境后，围绕“执行流量趋势”“任务详情列表时间筛选”“任务时间展示”“日志详情时间展示”暴露出一批体验与正确性问题。

本次迭代先不直接进入开发，而是先将问题收敛为一份可执行的需求文档，明确：

- 用户的原始反馈到底是什么
- 当前系统已实现到什么程度、哪里与需求不一致
- 本轮修复应落到哪些产品需求、交互需求、接口需求与技术方案
- 后续开发与验收应以什么为准

本轮文档对应的问题发现时间可按 **2026-04-03** 记录，问题来源为“上一版功能在正式环境部署后的回归观察”。

## 2. 用户原始需求记录

以下内容按用户原始表述整理，作为本轮迭代的输入源，不做改写：

### 2.1 原始问题 1：执行流量趋势模块粒度异常

- 之前需求是要支持 **按小时、按 5 小时、按天** 切换
- 现在切换 tab 少了
- 切换到按天之后，时间轴并未变化

### 2.2 原始问题 2：执行流量趋势模块缺少分系列控制

- 现在不支持分别展示 **核实执行** 和 **质检执行**
- 希望图表中的图例做成 **可交互式**
- 可以选择展示内容

### 2.3 原始问题 3：任务详情列表筛选粒度不够

- 现在只能按照日期进行筛选
- 希望支持 **按小时筛选**
- 希望给一些 **快捷选项**
- 希望从产品经理角度进一步优化交互设计

### 2.4 原始问题 4：任务详情列表排序与时间感知不足

- 上一版本增加了按时间排序
- 但当前“感知不明显”，不确定功能是否真的生效
- 具体任务现在没有时间展示，希望加上时间

### 2.5 原始问题 5：日志详情缺少时间信息

- 之前要求日志详情页加上时间展示
- 当前页面看起来没有体现

## 3. 当前现状复盘与问题确认

本节基于当前代码现状进行复盘，用于界定“已实现部分”和“真实缺口”。

### 3.1 执行流量趋势模块现状

#### 3.1.1 已实现部分

- 页面已有“执行流量趋势”卡片
- 页面已有粒度切换状态 `hour / day`
- 图表已同时绘制 `verifyCount` 与 `qcCount`
- 当前接口已返回 `timeSeries`

#### 3.1.2 已确认问题

- 当前前端只保留了 **按小时**、**按天** 两个切换项，**按 5 小时** 已丢失
- 当前“按天”切换只改变了 X 轴格式化文本，**未改变底层聚合逻辑**
- 当前图例虽然可见，但仍是 Recharts 默认图例，**未接入交互切换**
- 当前图表默认同时展示核实和质检，**无法做单系列观察**

#### 3.1.3 初步原因判断

- 当前趋势数据聚合仍按 **小时块** 返回
- `granularity` 仅参与前端 `tickFormatter`，没有传入后端参与真实聚合
- 图例未绑定本地显示状态，因此无法开关系列

### 3.2 任务详情列表筛选现状

#### 3.2.1 已实现部分

- 页面已有 `startTime / endTime` 筛选参数
- 前后端接口已能透传时间范围
- 当前筛选 UI 已落地到任务详情列表顶部

#### 3.2.2 已确认问题

- 当前筛选控件使用的是 `type="date"`，只能选日期，**无法精确到小时**
- 当前没有“最近 1 小时 / 最近 6 小时 / 最近 24 小时”等快捷范围
- 当前筛选区虽可用，但从使用效率上看，**仍偏底层参数型交互**，不够适合高频运营排查

### 3.3 任务详情列表排序现状

#### 3.3.1 已实现部分

- PostgreSQL 仓储已实现按 `qc_time > verify_time > updatetime` 的倒序排序
- 排序目标方向与上一版需求一致

#### 3.3.2 已确认问题

- 当前前端列表卡片上 **没有显式展示“用于排序的时间”**
- 用户无法直接判断“为什么这条任务排在前面”
- SQLite 仓储当前仍主要按 `updatetime` 排序，**与 PostgreSQL 逻辑未完全对齐**
- 因此“功能好像没有感知”不仅是展示问题，也存在 **双仓储实现不一致** 的风险

### 3.4 任务详情列表时间展示现状

#### 3.4.1 已实现部分

- 任务卡片展开后的核实模块、质检模块中，已有核实时间/质检时间、开始时间、结束时间等字段

#### 3.4.2 已确认问题

- 折叠态列表卡片没有展示关键时间
- 默认浏览列表时，无法快速识别：
  - 这条任务最近什么时候有动作
  - 是核实时间还是质检时间驱动了排序
  - 核实和质检各自的时间分布如何

### 3.5 日志详情页时间展示现状

#### 3.5.1 已实现部分

- 日志详情页已展示 task_id、session 数、当前阶段、日志状态

#### 3.5.2 已确认问题

- 页面未展示核实/质检的 **开始时间、结束时间、业务时间、耗时**
- 用户进入日志详情后，无法先在概览区快速建立时间上下文

## 4. 本轮设计目标

本轮修复不是简单补字段，而是围绕“看得见、筛得准、解释得通”三件事做统一优化。

### 4.1 正确性目标

- 切换时间粒度时，图表聚合结果必须真实变化
- 任务列表排序逻辑在 SQLite / PostgreSQL 下必须保持一致
- 时间筛选必须支持小时级查询

### 4.2 可感知目标

- 用户能明确感知当前图表处于哪种粒度
- 用户能明确理解任务列表是按什么时间排序的
- 用户能在任务列表与日志详情页直接看到关键时间

### 4.3 操作效率目标

- 高频排查场景下，尽量减少手工输入时间
- 支持快捷时间范围
- 保留自定义精确时间窗口

### 4.4 兼容性目标

- 继续兼容 SQLite 与 PostgreSQL
- 保持现有页面结构稳定，优先增量优化，不做大改版

## 5. 设计后的开发需求

## 5.1 执行流量趋势模块修复与增强

### 5.1.1 功能需求

- 趋势图必须支持以下 3 种粒度切换：
  - 按小时
  - 按 5 小时
  - 按天
- 粒度切换后，以下内容必须同步变化：
  - X 轴刻度
  - Tooltip 时间文案
  - 数据聚合结果
  - 点位数量
- 图例必须支持交互式切换：
  - 可只看核实执行
  - 可只看质检执行
  - 可同时看两者

### 5.1.2 交互设计

- 粒度切换保留为趋势图右上角分段按钮，顺序固定为：
  - 按小时
  - 按 5 小时
  - 按天
- 图例改为“可点击开关式图例”，交互规则如下：
  - 点击“核实执行”可切换核实系列显隐
  - 点击“质检执行”可切换质检系列显隐
  - 被关闭的系列在图例上显示弱化态
  - 至少保留一个系列为开启状态，避免出现空图
- 当只显示单系列时，图表标题与说明文案不变，避免整体结构抖动

### 5.1.3 数据口径

- 趋势图时间口径统一定义为：
  - 优先取执行日志 `started_at`
  - 若无日志时间，则回退业务表时间
    - 核实回退 `verify_time`
    - 质检回退 `qc_time`
- 三种粒度的定义：
  - 按小时：每 1 小时一个桶
  - 按 5 小时：按自然时间窗口聚合为 5 小时一个桶
  - 按天：按自然日聚合

### 5.1.4 接口需求

- `/api/dashboard/overview` 新增 `timeGranularity` 参数
- 枚举值：
  - `hour`
  - `five_hour`
  - `day`
- 返回结构保持兼容，继续返回：
  - `timeBlock`
  - `verifyCount`
  - `qcCount`

### 5.1.5 技术方案

- 后端承担真实聚合，不在前端做“按天只是换标签”的伪切换
- PostgreSQL 与 SQLite 分别实现统一口径的分桶 SQL
- 前端只负责：
  - 透传 `timeGranularity`
  - 渲染不同粒度的 X 轴/Tooltip
  - 维护图例显隐状态

## 5.2 任务详情列表时间筛选升级

### 5.2.1 功能需求

- 时间筛选需从“按日期”升级为“按日期 + 小时”
- 支持快捷时间范围
- 支持手动自定义时间点筛选
- 支持在需要时切换到完整时间段筛选

### 5.2.2 产品交互设计

考虑任务列表是高频排查区，建议采用“快捷范围 + 单时间点快筛 + 进阶时间段”三层设计，优先满足高频排查，再兼顾精细查询。

#### 第一层：快捷范围

建议提供以下快捷选项：

- 1 小时
- 5 小时
- 当天
- 全部

设计原则：

- 默认选中 **全部**
- 点击快捷项后，自动回填开始/结束时间
- 当前命中的快捷项需高亮显示

#### 第二层：单时间点快筛

- 将现有 `date` 输入框升级为 `datetime-local`
- 默认采用“单时间点 + 方向”的轻量交互：
  - `之后`
  - `之前`
- 交互规则：
  - 选择 `之后` 时，仅展示 1 个时间输入框，表示“查看该时间点之后的数据”
  - 选择 `之前` 时，仅展示 1 个时间输入框，表示“查看该时间点之前的数据”
  - 用户输入后，自动映射为 `startTime` 或 `endTime`
- 设计目标：
  - 降低高频排查时的输入成本
  - 避免用户一上来就面对“双时间框”的复杂心智负担

#### 第三层：进阶时间段

- 当用户需要更精细的窗口控制时，提供“时间段模式”入口
- 进入后展示完整双时间输入：
  - 开始时间
  - 结束时间
- 用户可在以下 3 种模式间切换：
  - `之后`
  - `之前`
  - `时间段`
- 切换为 `时间段` 后，才展示完整起止时间输入
- 用户手动修改后，快捷项自动切换为“自定义状态”

### 5.2.3 交互细节要求

- 快捷项区域固定展示，不因模式切换而位移明显
- 默认进入页面时，快捷项为 **全部**，自定义区域收敛为轻量状态
- `之后 / 之前 / 时间段` 应使用分段切换或 Tab 式切换，语义清晰
- 结束时间默认理解为“精确到分钟的包含边界”
- 清除筛选后恢复全量列表
- 若当前命中快捷项，则自定义模式展示为只读或自动回填后的可编辑状态
- 用户从快捷项切到自定义后，界面应明确标识“当前为自定义筛选”
- 时间筛选变更后：
  - 概览卡片同步刷新
  - 趋势图同步刷新
  - 任务列表同步刷新

### 5.2.4 接口与兼容性要求

- 继续使用 `startTime / endTime`
- 后端需兼容两类输入：
  - 旧格式日期字符串
  - 新格式日期时间字符串
- PostgreSQL / SQLite 的比较逻辑需保持一致

## 5.3 任务详情列表排序修复与时间可视化

### 5.3.1 功能需求

- 任务列表默认排序保持为：
  - 优先 `qc_time`
  - 次之 `verify_time`
  - 最后 `updatetime`
- SQLite 与 PostgreSQL 必须完全对齐
- 页面上必须显式展示与排序相关的时间信息

### 5.3.2 产品交互设计

为解决“排序没有感知”的问题，建议在任务卡片折叠态直接展示一组轻量时间信息。

#### 折叠态新增展示

- **最新动作时间**：作为主展示时间
- **时间来源标签**：显示该时间来自
  - 质检时间
  - 核实时间
  - 初始更新时间
- **核实时间**
- **质检时间**

#### 列表区域补充说明

- 在“任务详情列表”标题区补充一行说明：
  - 默认按最新动作时间倒序

这样用户即使不展开卡片，也能理解排序依据。

### 5.3.3 数据字段建议

建议后端在任务列表接口中显式返回：

- `latestActionTime`
- `latestActionType`

其中：

- `latestActionTime` 为用于排序的最终时间
- `latestActionType` 枚举建议为：
  - `qc`
  - `verify`
  - `init`

### 5.3.4 技术方案

- PostgreSQL 保持现有排序方向，但补齐返回字段
- SQLite 仓储改为与 PostgreSQL 相同的排序口径
- 前端不自行推导排序字段，直接消费后端返回的显式字段，减少口径分叉

## 5.4 日志详情页时间展示补齐

### 5.4.1 功能需求

- 日志详情页需补充核实与质检两个阶段的关键时间信息
- 至少覆盖：
  - 开始时间
  - 结束时间
  - 业务时间
  - 耗时

### 5.4.2 产品交互设计

建议在当前“日志总览”区域中，为核实和质检各增加时间摘要，不改变页面主结构。

#### 推荐展示方式

- 保留现有“核实日志 / 质检日志 / 当前阶段 / 日志状态”四张摘要卡
- 在每张阶段卡内追加：
  - 开始时间
  - 结束时间
  - 耗时
- 若业务表时间存在，可补充一行“业务时间”

这样可以保持现有视觉结构稳定，同时满足时间可见性要求。

### 5.4.3 接口需求

建议扩展任务日志详情接口，返回阶段级摘要信息，例如：

- `verifySummary`
  - `startedAt`
  - `endedAt`
  - `businessTime`
  - `durationMs`
  - `status`
- `qcSummary`
  - `startedAt`
  - `endedAt`
  - `businessTime`
  - `durationMs`
  - `status`

## 6. 开发方案

## 6.1 后端方案

### 6.1.1 趋势图粒度

- 在 `DashboardFilters` 或 `getOverview` 入参中增加 `timeGranularity`
- PostgreSQL：
  - 按小时：按小时分桶
  - 按 5 小时：基于时间戳整除 5 小时窗口分桶
  - 按天：按自然日分桶
- SQLite：
  - 使用 `strftime` 与 Unix 时间戳整除实现相同分桶逻辑

### 6.1.2 时间筛选

- 统一解析 `startTime / endTime`
- 明确“开始时间 >=，结束时间 <=”的语义
- 兼容日期字符串与日期时间字符串

### 6.1.3 列表排序与返回字段

- PostgreSQL：
  - 保留 `COALESCE(qc_time, verify_time, updatetime)` 排序
  - 增加 `latestActionTime / latestActionType`
- SQLite：
  - 从仅按 `updatetime` 排序修正为与 PostgreSQL 同口径排序
  - 同步补齐 `latestActionTime / latestActionType`

### 6.1.4 日志详情摘要

- 在 `getTaskLogDetail` 中增加阶段摘要字段
- 摘要数据优先来自最新阶段运行记录，必要时回退业务时间

## 6.2 前端方案

### 6.2.1 趋势图

- 新增 `按 5 小时` 粒度按钮
- 将粒度状态接入接口请求
- 自定义图例点击逻辑，维护系列可见状态

### 6.2.2 任务列表筛选

- 时间输入框升级为 `datetime-local`
- 增加快捷范围按钮组
- 在 URL 查询参数中继续持久化时间范围，保证可分享、可刷新恢复

### 6.2.3 任务列表卡片

- 折叠态增加最新动作时间区
- 增加排序说明文案
- 保持展开态中的详细时间卡片不变，只做补充，不推翻现有结构

### 6.2.4 日志详情

- 在总览摘要卡中加入时间信息
- 阶段切换按钮仍保持原结构，仅补充时间上下文

## 7. 验收标准

## 7.1 执行流量趋势

- 切换“按小时 / 按 5 小时 / 按天”后，图表柱点数量与时间轴标签均发生真实变化
- “按天”模式下，不再出现只是文案变化、数据点不变的情况
- 图例可点击控制系列显隐
- 仅展示核实执行或仅展示质检执行时，图表仍可正常渲染

## 7.2 任务列表时间筛选

- 可按小时级时间窗口筛选任务
- 快捷项可一键切换 `1 小时 / 5 小时 / 当天 / 全部`
- 默认进入页面时选中 `全部`
- 自定义筛选支持 `之后 / 之前 / 时间段` 三种模式，且切换逻辑清晰，不出现状态错乱

## 7.3 任务列表排序与时间展示

- PostgreSQL 与 SQLite 下，同样的数据集排序结果一致
- 列表首屏即可看到每条任务的最新动作时间
- 用户能从界面中判断当前排序依据

## 7.4 日志详情时间展示

- 日志详情页可直接看到核实和质检阶段的关键时间
- 当某阶段无日志时，页面显示明确的空值说明，不出现误导

---

## 8. 风险与注意事项

### 8.1 时间格式与时区

- `datetime-local` 不自带时区信息
- 前后端需要统一按当前系统时区解释，避免出现筛选边界偏移

### 8.2 5 小时分桶口径

- 需明确按自然时间整块聚合，而不是简单每 5 条数据合并
- Tooltip 与 X 轴文案必须体现对应时间窗口，避免误读

### 8.3 双仓储一致性

- 本轮问题中，SQLite 与 PostgreSQL 逻辑不一致是一个真实风险
- 后续验收必须双环境都覆盖

### 8.4 可视化复杂度控制

- 本轮目标是“增强理解力”，不是把页面做成复杂 BI 工具
- 所有新增交互应尽量轻量，保持现有看板风格

---

## 9. 建议实施顺序

1. 先修复后端趋势图真实聚合与任务排序口径
2. 再补前端粒度切换、交互图例、时间筛选升级
3. 然后补任务列表与日志详情的时间展示
4. 最后做 PostgreSQL / SQLite 双环境回归验收
