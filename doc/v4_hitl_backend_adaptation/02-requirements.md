# 需求文档：HITL 页面回归展示与回归详情页

## 1. 背景与目标

当前 `HITL 迭代运营页` 已具备页面骨架，能够表达从反馈池到迭代处理的整体闭环，但回归验证部分仍未形成真实的产品设计与后端接入约束。随着 `example/hitl` 下回归相关库表规格和样例数据补齐，并且三张回归表已统一增加 `batch_id` 字段，本轮需要把回归部分从“占位区块”推进为可落地的正式需求。

本轮目标是基于现有 HITL 主链路与回归三表，完成以下三件事：

1. 在 `HITL` 主页面补充回归区展示，明确核实回归与质检回归的展示口径
2. 新增回归详情页，用于展示某次回归运行下的差异明细，并突出新旧结果对比
3. 在主页面补充“最终结论”决策区，基于核实 / 质检回归指标给出上线、回滚或人工复核建议

本轮不新增业务元数据表，不引入新的回归计算逻辑，直接消费已有回归结果表与回归对比表。

涉及数据表：

- `iteration_negative_samples`
- `iteration_overlay_drafts`
- `iteration_skill_modifications`
- `poi_verified_regression_test`
- `poi_verified_regression_test_compare`
- `poi_verified_regression_test_result`

其中本轮回归展示的主数据来源为：

- `poi_verified_regression_test_result`：回归汇总指标
- `poi_verified_regression_test_compare`：回归差异明细
- `poi_verified_regression_test`：样本级补充详情

---

## 2. 用户已确认的核心口径

### 2.1 批次口径

- 回归数据已通过 `batch_id` 与 HITL 主批次打通
- 本轮样例数据统一按 `batch_0415` 归属
- 主页面回归区与回归详情页都应以 `batchId` 为一级查询条件

### 2.2 回归区展示口径

主页面回归区拆分为两张卡片：

1. `核实回归`
2. `质检回归`

每张卡片只展示本类型核心指标，不混合展示其它维度。

### 2.3 核实回归指标口径

核实回归卡片主要展示：

- `verify_better_ratio`
- `verify_worsen_ratio`

必要时可补充：

- `positive_count`
- `negative_count`
- `total_count`

但主展示重点仍是“变好 / 变差”比例。

### 2.4 质检回归指标口径

质检回归卡片主要展示：

- `qc_better_ratio`
- `qc_worsen_ratio`

必要时可补充：

- `positive_count`
- `negative_count`
- `total_count`

但主展示重点仍是“变好 / 变差”比例。

### 2.5 详情页入口口径

- 主页面的 `核实回归` 卡片提供“查看详情”
- 主页面的 `质检回归` 卡片提供“查看详情”
- 两个入口都跳转到专属回归详情页
- 详情页按 `regressionType` 区分核实 / 质检视角

### 2.6 回归详情页口径

回归详情页不是简单平铺样本列表，而是一个以“新旧差异对比”为核心的分析页。

页面需要明确展示：

- 旧结果是什么
- 新结果是什么
- 哪些样本发生了变化
- 变化属于变好还是变差
- 用户如何进一步查看样本级上下文

### 2.7 最终结论口径

最终结论区不再保持“待补充”占位，而是基于回归指标给出决策型结论。

页面需要突出：

- 当前建议是 `上线`、`回滚` 还是 `人工复核`
- 为什么得出该结论
- 结论主要受核实回归还是质检回归影响

最终结论区的展示目标不是再重复一遍指标，而是把指标翻译成可执行决策。

---

## 3. 当前现状与问题确认

### 3.1 前端现状

- `/hitl-iterations` 已有回归区视觉结构，但仍依赖前端 mock 或占位内容
- 当前没有专属回归详情页
- 当前也没有围绕“差异对比”设计的表格与详情交互

### 3.2 后端现状

- 已有主页面相关聚合接口雏形，但回归区仍未完成真实接入
- 还没有专门面向回归详情页的接口结构
- 还未统一回归摘要、回归差异、样本详情三层数据的返回口径

### 3.3 数据现状

三张回归表职责已较清晰：

- `poi_verified_regression_test_result`：按回归运行输出聚合结果，用于主页面卡片与详情页头部指标
- `poi_verified_regression_test_compare`：按样本输出新旧结果对比，用于详情页主表
- `poi_verified_regression_test`：按样本保存更完整上下文，用于详情页二级展开或抽屉详情

当前关键约束是：

- 详情页必须围绕“旧值 vs 新值”组织信息
- 主页面只做摘要，不在卡片内堆叠过多字段
- 明细页的表格字段需要根据核实 / 质检类型切换重点列

---

## 4. 本轮产品需求

## 4.1 主页面回归区需求

### 4.1.1 展示位置

回归区继续位于 `HITL` 页面流程区之后，作为“回归验证”步骤的核心展示内容。

### 4.1.2 展示结构

主页面回归区至少包含两张摘要卡：

1. `核实回归卡`
2. `质检回归卡`

每张卡建议包含以下信息：

- 回归类型名称
- 回归运行时间
- 数据集或运行标识
- 样本总量
- 变好比例
- 变差比例
- “查看详情”入口

### 4.1.3 核实回归卡需求

核实回归卡最小展示集：

- 标题：`核实回归`
- `verify_better_ratio`
- `verify_worsen_ratio`
- `total_count`
- `runAt` 或回归时间
- `datasetName` 或运行标识

卡片目标：

- 让用户快速判断核实能力是否回归变差
- 支持一键下钻到核实回归详情页

### 4.1.4 质检回归卡需求

质检回归卡最小展示集：

- 标题：`质检回归`
- `qc_better_ratio`
- `qc_worsen_ratio`
- `total_count`
- `runAt` 或回归时间
- `datasetName` 或运行标识

卡片目标：

- 让用户快速判断质检能力是否回归变差
- 支持一键下钻到质检回归详情页

### 4.1.5 主页面交互需求

- 两张卡都支持点击“查看详情”
- 下钻时需带上：
  - `batchId`
  - `regressionType`
  - `datasetName`
  - 运行时间或运行标识
- 若同一批次下存在多次回归运行，主页面默认展示最近一次结果

---

## 4.2 回归详情页需求

### 4.2.1 页面入口

建议路由包含：

- `batchId`
- `regressionType`
- `datasetName`
- `runId` 或时间标识

页面定位：

- `regressionType = verify` 时，进入核实回归详情页
- `regressionType = qc` 时，进入质检回归详情页

### 4.2.2 页面目标

回归详情页的核心目标不是再次展示汇总值，而是帮助用户判断：

- 这次回归具体改变了哪些样本
- 改变发生在什么字段
- 变化方向是变好还是变差
- 是否需要进一步查看样本级上下文

### 4.2.3 页面结构

回归详情页至少包含四块：

1. 页首基础信息区
2. 指标摘要区
3. 差异明细表
4. 样本详情区

### 4.2.4 页首基础信息区

至少展示：

- `batchId`
- 回归类型
- `datasetName`
- 回归运行时间
- 样本总量
- 当前筛选条件摘要

### 4.2.5 指标摘要区

根据回归类型展示对应指标：

当 `regressionType = verify`：

- `verify_better_ratio`
- `verify_worsen_ratio`
- `positive_count`
- `negative_count`
- `total_count`

当 `regressionType = qc`：

- `qc_better_ratio`
- `qc_worsen_ratio`
- `positive_count`
- `negative_count`
- `total_count`

### 4.2.6 差异明细表需求

差异明细表是页面主体，必须突出“旧值 / 新值”的对比。

明细表至少满足以下要求：

- 显示样本标识，如 `task_id`、`id`、POI 基础信息
- 显示变化方向，如 `变好 / 变差 / 无变化`
- 显示旧值与新值
- 支持只看有变化样本
- 支持按 `变差优先` 排序
- 支持查看单条样本详情

### 4.2.7 核实视角明细字段

当 `regressionType = verify`，表格重点字段至少包括：

- `compare_verify_result` 或拆分后的旧值 / 新值
- `compare_qc_status` 可弱化展示
- `sample_type`
- `is_consistent`
- 变化方向
- 样本详情入口

页面重点应放在核实结果的前后变化，而不是质检状态。

### 4.2.8 质检视角明细字段

当 `regressionType = qc`，表格重点字段至少包括：

- `compare_qc_status` 或拆分后的旧值 / 新值
- `compare_verify_result` 可弱化展示
- `sample_type`
- `is_consistent`
- 变化方向
- 样本详情入口

页面重点应放在质检状态的前后变化，而不是核实结论。

### 4.2.9 样本详情区需求

点击某条明细后，支持展开详情抽屉或详情面板，展示：

- 样本基础信息
- 旧结果与新结果的完整上下文
- 核实信息 / 质检信息
- 证据或说明字段
- 必要的人工标注结果

样本详情区应进一步强化新旧差异，而不是只展示当前值。

---

## 4.3 差异展示专项需求

### 4.3.1 核心原则

回归详情页必须把“对比”当作一等公民，而不是把旧值和新值埋在原始 JSON 或长文本里。

### 4.3.2 展示要求

- 表格列优先直接展示 `旧值 -> 新值`
- 如果底表只有组合字符串，也需要在展示层拆解成 `旧值`、`新值`
- 发生变化的行需要有明显视觉标识
- `变差` 行优先级高于 `变好` 行
- 无变化行默认可以折叠、弱化或作为筛选结果出现

### 4.3.3 方向判断要求

页面需要能明确表达：

- 哪些变化是 `better`
- 哪些变化是 `worsen`
- 哪些变化是 `consistent`

如果底表未直接提供方向字段，后端或前端展示层需基于对比字段补充推导。

---

## 5. 非功能要求

### 5.1 一致性要求

- 主页面与详情页的指标口径必须一致
- 同一回归运行下，摘要指标与明细总量必须可对齐
- `batchId`、`datasetName`、运行时间等上下文参数必须稳定透传

### 5.2 可扩展性要求

- 后续若增加新的回归维度，允许在当前核实 / 质检框架下继续扩展
- 回归详情页的差异展示逻辑应可复用，不应只适配一套字段

### 5.3 可读性要求

- 主页面卡片不堆叠过多技术字段
- 详情页优先让用户快速发现“变差样本”
- 长文本、JSON、证据信息需支持折叠或分区展示

---

## 6. 本轮交付范围

本轮需求文档确认以下交付项：

1. 主页面回归区正式接入方案
2. 核实回归 / 质检回归双卡展示口径
3. 回归详情页展示目标与页面结构
4. 差异对比作为详情页核心展示原则
5. 后续开发所需的字段与交互约束

本轮不要求完成：

- 新回归算法设计
- 结果判责规则重算
- 独立的配置治理后台


## 4.3 最终结论区需求

### 4.3.1 展示位置

最终结论区位于主页面回归区之后，作为本轮 HITL 迭代是否建议继续推进发布的决策展示区。

### 4.3.2 展示结构

最终结论区至少包含两部分：

1. 决策主卡
2. 结论原因列表

### 4.3.3 决策主卡需求

决策主卡需要突出单一结论，不应设计成普通信息卡。

主展示内容至少包括：

- 结论类型：`建议上线` / `建议回滚` / `建议人工复核`
- 结论摘要
- 结论对应的回归运行时间
- 结论涉及的关键指标摘要

### 4.3.4 原因列表需求

原因列表需要解释结论来源，至少支持：

- 核实回归是否出现变差
- 质检回归是否出现变差
- 是否存在正向收益支持上线
- 是否存在冲突信号导致只能人工复核

每条原因建议包含：

- 原因标题
- 原因说明
- 严重级别
- 对应指标值

### 4.3.5 决策推导需求

在没有独立决策表的前提下，最终结论由后端基于回归指标聚合推导。

建议遵循以下方向：

- 任一关键维度明显变差时，优先给出 `建议回滚`
- 核实与质检均稳定且存在正向收益时，可给出 `建议上线`
- 当核实与质检信号冲突或结果不明确时，给出 `建议人工复核`

本轮先确认展示结构与返回字段，不在需求文档中硬编码具体阈值。
